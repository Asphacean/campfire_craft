## The one correction this plan makes to a locked decision, and why

D-05 and the phase's headline constraint say the real signing key never reaches GitHub. `05-CONTEXT.md` and RESEARCH both assumed the way to honour that is `--no-sign` on every build leg. Reading the pinned CLI and bundler sources on this Pi during planning showed that flag would also switch off the ad-hoc macOS codesign D-08 requires:

- `~/.cargo/registry/src/index.crates.io-*/tauri-bundler-2.9.4/src/bundle/macos/app.rs:115` — when the no-sign setting is on, the macOS app bundle signing block is skipped entirely, ad-hoc identity or not.
- `~/.cargo/registry/src/index.crates.io-*/tauri-cli-2.11.4/src/bundle.rs:255` — the no-sign setting only short-circuits `sign_updaters`, which runs *after* `tauri_bundler::bundle_project` has already written every bundle.
- `.../tauri-cli-2.11.4/src/bundle.rs:303` — a private key whose key id does not match the configured public key produces a **warning**, not an error.

Those three facts together give a better answer, which the tasks below implement: **do not pass the no-sign flag; generate a throwaway keypair inside the CI run instead.** The updater gate is satisfied, ad-hoc macOS signing still happens, the resulting `.sig` files are never uploaded, and the real key stays on the Pi — which is what D-05 actually protects. RESEARCH's Open Question 1 (does the updater `.app.tar.gz` still get produced?) is answered by `bundle.rs:206-225`: the updater bundle is built by the bundler before any signing happens, so it exists either way. Task 2 proves the whole recipe locally before any CI minute is spent on it.
