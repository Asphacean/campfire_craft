### 3. Next release exercises the CR-01 checksum gate (non-blocking follow-up)
expected: On the next scripts/release.sh tag, the publish job verifies assets against the build job's checksums artifact before signing (watch the run once).
result: [passed] 2026-08-31: v0.1.5 release run fully green incl. publish job — CR-01 checksum gate executed live (build-job checksums artifact verified before signing); feed auto-updated to 0.1.5 (darwin-aarch64 + windows-x86_64, Intel leg retired).
  - **v0.1.1** (`596bcae`): `build (macos-14)` failed at the CR-01 checksum-recording step — macOS runners have no `sha256sum` (GNU coreutils; this image's GNU tools are `g`-prefixed) and `xargs --no-run-if-empty` is a GNU-only long option BSD/macOS `xargs` rejects outright. `build (windows-latest)` passed only because Git-for-Windows ships GNU coreutils, masking the defect there. **Diagnosed + fixed**, commit `279cc03` (branch on `$RUNNER_OS` for `shasum -a 256` vs `sha256sum`; `find -exec {} +` instead of `xargs`, which never invokes the hash command when nothing matches, on both BSD and GNU `find`).
  - **v0.1.2** (`fa2f74a`): all three `build` legs passed (confirms the v0.1.1 fix), but `publish` (self-hosted, this Pi) failed: `curl` exit 22 (HTTP failure under `-f`) on either the release-lookup GET or an asset download. This runner shares its public IP with this Pi's own unauthenticated GitHub API polling (used to watch this very run) — a transient 403 (60/hour unauthenticated rate limit) or a brief asset-CDN propagation 404 right after upload is a real, plausible cause; manually reproducing the same two `curl` calls minutes later succeeded cleanly. **Fixed**, commit `646e7f4` (`--retry 5 --retry-delay 5 --retry-all-errors` on both `publish` job `curl` calls).
  - **v0.1.3** (`b2772e7`): all three `build` legs passed again. `publish` failed with `Process completed with exit code 1` after only ~2.7s of runtime (per `_diag/Worker_20260831-003757-utc.log`) — too fast for the retried `curl` calls to have needed a retry, meaning the script reached its own checksum-verification `exit 1` guard almost immediately. **Root cause fully confirmed** (2026-08-31), directly against the real checksum artifacts this failed run left behind at `~/actions-runner-campfire/_work/campfire_craft/campfire_craft/checksums/*.txt` (never cleaned up, so still readable without any GitHub auth): two independent, concurrent filename-matching bugs, either alone sufficient to trip "no known-good checksum for `$f` — refusing to sign":
    1. **Windows path-stripping bug.** `checksums-windows-latest.txt` held full repo-relative paths (`launcher/target/release/bundle/nsis/Campfire-Launcher_0.1.3_x64-setup.exe`), not bare filenames, because windows-latest's `sha256sum` emits binary-mode output (`<hex> *<path>`, one space + asterisk) rather than GNU's default text-mode (`<hex>  <path>`, two spaces) that the old `sed -E 's|(  ).*/|\1|'` required to fire at all.
    2. **macOS updater-bundle naming gap.** `checksums-macos-14.txt` / `checksums-macos-15-intel.txt` contained sha256 entries for the `.dmg` files only — zero entries for either `.app.tar.gz` updater bundle, even though both exist as real, correctly-named release assets (confirmed via the GitHub API). The `.dmg`'s local on-disk filename already carries version+arch (matching the release asset name by coincidence); the `.app.tar.gz`'s apparently does not.
    - **Verified directly**: downloaded the actual v0.1.3 release assets and recomputed their sha256; the Windows `.exe`/`.msi` hashes match the (mis-formatted) checksums file content exactly, and the two `.app.tar.gz` hashes have no entry anywhere in the checksums artifacts at all — reproducing the exact "no known-good checksum" condition byte-for-byte.
    - **Fixed**, commit `dedc1ea`: (a) the build job's path-stripping `sed` now matches both the GNU text-mode and Windows binary-mode `sha256sum` line formats; (b) the publish job's verify step now matches downloaded assets against the checksums artifact by **sha256 membership** rather than exact filename, which is invariant to any future local-name-vs-release-asset-name mismatch. `actionlint -config-file .github/actionlint.yaml` passes clean; the new sed and hash-membership logic were both re-run locally against this run's real captured checksum lines and downloaded v0.1.3 bytes with the expected pass/fail behavior.
  - **Local-publish note (this session, 2026-08-31):** to prove the fixed logic's *intent* without spending a fourth `scripts/release.sh` tag, ran `scripts/publish-launcher.sh` by hand — the exact command `release.yml`'s publish job runs — against the real v0.1.3 release assets downloaded anonymously from GitHub. Result: `https://mc.campfire.pub:8444/launcher/latest.json` now reports `version: "0.1.3"`, all 3 platform URLs return HTTP 200, all 3 downloaded sha256s match the GitHub release assets exactly, and a from-scratch minisign verifier (Python + `cryptography`, since no `minisign` binary or `pynacl` is installed on this Pi) confirms every platform's per-file Ed25519 signature (the `ED`/prehashed variant Tauri's updater actually uses) validates against the pubkey baked into `launcher/src-tauri/tauri.conf.json`. **This proves the artifacts, signing key, and feed format are all correct** — it does NOT prove the CI publish job itself now succeeds end-to-end; that is only provable on the next tagged release, per the retry-budget rule.

### 6. Mac v0.1.7 "fetching Minecraft files failed" (gap-closure #4)
expected: Play on Mac reaches the "Fetching Minecraft files" step and succeeds; if it fails, the log names what actually broke.
result: [issue] Reported 2026-08-31 against v0.1.7: after sync completed and Java provisioned (x64 under Rosetta), `play: fetching Minecraft files failed: Io("No such file or directory (os error 2)")` — no path in the error at all. Real Mac game root always contains a space (`~/Library/Application Support/campfire/game`), so the leading hypothesis was a space/parent-dir handling bug.
  - **Reproduced on the Pi first, as instructed.** Built a scratch `CAMPFIRE_HOME` containing a space and ran the exact pipeline: `campfire-cli vanilla`, `campfire-cli forge` (via the `CAMPFIRE_FORGE_JAVA` test escape hatch pointed at the Pi's Temurin 8), and the full `campfire-cli play --nick <throwaway> --ram 3 --no-spawn` sequence — all six steps completed cleanly, argv built correctly with the space intact as one argument. **The space hypothesis is disproven, not guessed away**: `mojang.rs`/`forge.rs`/`launch.rs` already build every path via `PathBuf::join` and pass every `Command` arg as a separate `OsStr`, never a shell string or string concatenation.
  - Audited all four play-pipeline modules (`mojang.rs`, `forge.rs`, `launch.rs`, `java.rs`) for the class of bug the symptom actually points at — `io::Error`'s own `Display` never names the path or operation it failed on, so `Io("No such file or directory (os error 2)")` is exactly what *any* path-blind ENOENT (a missing file, or a `Command::spawn()` on a binary that isn't there) looks like from a dozen different call sites, with zero way to tell which. Found and fixed two real defects, commit `ee89cf9`:
    1. Every `io::Error` in the four modules was wrapped as a bare `e.to_string()`. Now every fs/process call routes through a shared `paths::io_ctx(op, path, e)` helper that always names both.
    2. Every tmp-file name in `mojang.rs`/`java.rs` was suffixed with bare `std::process::id()` alone — identical for every concurrent async task inside one process. Two tasks racing to write the same destination (e.g. two overlapping `ensure_vanilla`/`ensure_java` calls) shared the same tmp path; whichever renamed first left the other's later `rename`/`remove_file` hitting a bare, path-less ENOENT — a plausible source of exactly this symptom class, though not confirmed as the friend's specific trigger (checked the frontend: `setPlayBusy(true)` disables the Play button synchronously before any `await`, so a same-window double-click can't reach it — a genuine concurrency hardening either way, not a confirmed root cause). Fixed with a process-wide atomic counter (`paths::unique_tmp_suffix()`).
  - Added a Pi-runnable, `#[ignore]`'d live-network integration test driving vanilla bootstrap + Forge install into a scratch space-containing `CAMPFIRE_HOME`, plus unit tests for `io_ctx`, `unique_tmp_suffix`, and every `paths.rs` dir helper under a space-containing home. `cargo test --workspace` (3 consecutive runs, no flakes), `clippy -D warnings`, `cargo tauri build --no-bundle` all green. Re-verified the full `play --no-spawn` pipeline on the Pi against the rebuilt binary in a fresh space-containing scratch dir — still green.
  - **Root cause of the friend's exact failure is not confirmed.** The leading hypothesis was tested and disproven with live reproduction, not assumed away; the two defects fixed are real and shipped regardless, and the observability fix is specifically what will name the exact path/operation if this recurs. **v0.1.8 released** (tag `681ba2c`, `release.yml` run [33385586186](https://github.com/Asphacean/campfire_craft/actions/runs/33385586186) fully green — build macos-14, build windows-latest, publish all `success`, first attempt). Both feeds confirmed byte-for-byte identical: `curl --cacert ca/campfire-ca.pem https://mc.campfire.pub:8444/launcher/latest.json` and `curl -sL https://github.com/Asphacean/campfire_craft/releases/latest/download/latest.json` both return `version: "0.1.8"`, `pub_date: "2026-08-31T11:27:52Z"`, identical `darwin-aarch64`/`windows-x86_64` signatures. **Awaiting a Mac re-test on 0.1.8** — if the failure recurs, `launcher.log` will now name the exact path and operation, which is what actually closes this gap.

### 7. Mac v0.1.9 SIGSEGV deep in mods (gap-closure #5)
expected: Play on Apple Silicon Mac (Rosetta) reaches the world and stays up under normal mod load — no native-code crash after the Mojang splash.
result: [issue] Reported 2026-08-31 against v0.1.9: game launched under x86_64 Temurin 8 + Rosetta, loaded deep into mods, then SIGSEGV pc=0x0 in native code. Initial hypothesis (04-CONTEXT's deferred spike): the general LWJGL2-under-Rosetta pitfall (PITFALLS.md Pitfall 5), fixable only by a full ARM64-native LWJGL2 rebuild.
  - **Root cause confirmed, not assumed**, from the operator's own `hs_err`: `SIGSEGV` at `Java_org_lwjgl_openal_EFX10_nalGenFilters2` inside LWJGL2's own `liblwjgl.dylib` (thread "Thread-11", `_thread_in_native`). An RLCraft sound mod calls OpenAL EFX (`alGenFilters`); the `openal.dylib` LWJGL2 resolves on macOS has no EFX support (Apple's own `OpenAL.framework` has never implemented it), so the JNI stub calls a null extension-function pointer. This is an **OpenAL problem, not an architecture problem** — it would hit a hypothetical native-arm64 LWJGL2 build exactly as hard as the current x86_64-under-Rosetta one, since both would still be missing real EFX support without this fix.
  - **Researched a trustworthy prebuilt ARM64-native LWJGL2+jinput binary** (per the original task's own escape hatch: "if no trustworthy build can be verified, stop and say so — do not ship an unverified binary blob"). The only two canonical sources (`shadowfacts/lwjgl2-arm64`, `shadowfacts/jinput-arm64` — the forks PITFALLS.md itself names) publish **source only**, no releases or CI artifacts; building requires Xcode/Ant/Maven on an actual Mac, unverifiable and undoable from this Pi within the research budget. **Not shipped** — the arm64-native LWJGL2 swap (and the paired Zulu 8 arm64 JRE switch) remains an explicit deferred spike, unchanged from 04-CONTEXT.md. Switching only the JRE to arm64 without matching arm64 natives would be strictly worse (an immediate `UnsatisfiedLinkError: wrong architecture` before the game even starts) than today's deep-crash, so `java.rs`'s target matrix (D-10, x86_64 for both Mac targets) is untouched.
  - **Fixed the confirmed root cause instead**: a new `launcher/core/src/openal.rs` module fetches, sha256-verifies, and caches a real EFX-capable `openal-soft` build (Homebrew core's own bottle, published as a content-addressed OCI artifact on `ghcr.io`; pinned to version 1.25.2 and one exact blob digest, verified by hand this session against `formulae.brew.sh`'s own JSON API and a live re-download reproducing the identical sha256). `launch.rs::build_launch_command` overwrites the natives dir's `openal.dylib` with it right after Mojang's own natives extract, on both Mac targets (both provision an x86_64 JRE per D-10, so one x86_64 dylib covers both — no arm64 build needed for this fix specifically). Network-gated to `#[cfg(target_os = "macos")]`; every other platform compiles to a stub that makes no `ghcr.io` call at all. A `ghcr.io` hiccup at Play time logs and degrades to no override rather than blocking Play (network flakiness on an independent fix must not regress the rest of the sequence).
  - Unit-tested the natives-dir overwrite against a scratch dir with a fake pre-existing `openal.dylib` (proves the real file gets replaced, not merged or left alongside) and the non-macOS stub's zero-network-call guarantee. `cargo test --workspace` (44 lib + 14 launch_command + 12 manifest_guard, all green), `clippy --workspace --all-targets -D warnings` clean, `cargo tauri build --no-bundle` succeeds.
  - **Awaiting a Mac re-test on the next release** — this Pi has no display or Mac hardware to confirm the EFX crash is actually gone; the fix is unverifiable past the code/build/test level from here.
