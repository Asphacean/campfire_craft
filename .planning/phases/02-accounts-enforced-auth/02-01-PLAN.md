<objective>
Stand up `campfire-auth`: a Rust HTTP service on 127.0.0.1:8081 that registers accounts, issues short-lived single-use tokens, and answers the one question the game server will ask on every join — "is this nick presenting a token I issued?".

**Goal (quoted verbatim from ROADMAP.md Phase 2** — this Goal line is not in `As a` / `I want to` / `so that` user-story form; nothing has been invented in its place**):** *Only a registered nick presenting a valid token can play; anyone with a vanilla client is turned away.*

Purpose: AUTH-01 and AUTH-02, and the source of truth the Phase-2 mod defers to. Nothing in this plan touches the running game server — the service is additive and loopback-only (D-16), so it can be built, restarted and tested at any hour without affecting players.
Output: a service under systemd, a repeatable API assertion suite, accounts in the six-hourly backup, and a written API contract Phase 3 and Phase 4 build against.

## Phase 2 Decision IDs

These IDs are local to Phase 2 and are derived from `02-CONTEXT.md`. They are numbered independently of Phase 1's D-01…D-16.

| ID | Decision (from 02-CONTEXT.md) |

| D-04 | Nick `^[A-Za-z0-9_]{3,16}$`, unique case-insensitively; password ≥ 8 chars; 5 registrations/hour per IP; open self-registration |

| D-08 | Client reads `-Dcampfire.nick` / `-Dcampfire.token` and sends them over a `SimpleNetworkWrapper` channel |
| D-09 | Server freezes the player on join, waits ≤ 5 s for the packet, calls `/validate`; any failure kicks. Fail-closed always |
| D-10 | No operator bypass list; emergency access is RCON |
| D-11 | Manual test path: `campfire-auth login <nick>` plus a hand-launched client with the `-D` flags; the same client without the flags must be kicked |

    Install the toolchain, then build the thinnest complete path through every layer of the auth service: HTTP request → JSON extractor → argon2id → SQLite → HTTP response. One path, wired for keeps — production-quality crypto and SQL from the first commit. Rejection paths, rate limiting, `/status` and the CLI are Task 2's job and are absent here; nothing in this task may be written in a way that has to be torn out to add them.

    Toolchain: `sudo apt install -y cargo rustc sqlite3`. Do not install rustup — the apt toolchain is sufficient per RESEARCH.md's Environment Availability table.

    Create the crate at `auth-service/` with binary name `campfire-auth`. Direct dependencies, and only these: `axum`, `tokio` (features `rt-multi-thread`, `macros`), `rusqlite` (feature `bundled`), `argon2`, `serde` (feature `derive`), `serde_json`, `base64`. Every one of these is `Approved` in RESEARCH.md's Package Legitimacy Audit. Do **not** add `clap` (it is the audit's only unverified entry, and two subcommands do not need an argument parser — match on the first argument directly), do not add `sqlx`, and do not add a random-number crate: take the OS CSPRNG that argon2's `password-hash` dependency already re-exports (`rand_core::OsRng`), and only if that path does not exist in argon2 0.6.0 add `getrandom`, which is also in the audit's source list. Resolve the actual published versions with `cargo add` rather than hand-writing version strings, then commit `Cargo.lock` — the lockfile is this project's supply-chain pin.

    `src/db.rs` owns SQLite. One `rusqlite::Connection` behind a `Mutex` inside the shared axum state — no pool, no async SQLite wrapper; there are seven users and one writer. On open: `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=5000`, `PRAGMA foreign_keys=ON`, then create the schema if absent. Two tables. `users`: `id` integer primary key, `nick` text (the exact casing the player registered with — Pitfall 5 makes this load-bearing, because the game derives the offline UUID from the exact byte string and a case difference silently orphans a player's inventory), `nick_lower` text NOT NULL UNIQUE (the case-insensitive uniqueness index required by D-04), `pw_hash` text, `created_at` integer. `tokens`: `id` integer primary key, `user_id` integer referencing `users(id)`, `token_hash` text, `expires_at` integer, `consumed_at` integer NULL, `created_at` integer. All timestamps are Unix epoch seconds from `SystemTime`; do not add a date-time crate.

    Every statement in this file binds its inputs as SQL parameters. No user-supplied value is ever spliced into a query string — this is the Tampering mitigation the threat register gates on, and the gate is a grep, so there must not be a single string-built SQL statement anywhere in the crate.

    `src/auth.rs` owns the crypto, using `Argon2::default()` (argon2id, sensible parameters) and the 0.6.0 API where `hash_password` generates its own salt and `to_string()` yields the PHC string to store — do not copy the older salt-generation ceremony that 0.4/0.5-era examples show. Three functions: hash a secret, verify a secret against a stored PHC string, and generate a token as 32 bytes from the OS CSPRNG encoded with base64's `URL_SAFE_NO_PAD` engine. Tokens are hashed with the same argon2id path before storage (D-03) — the raw token exists only in the login response and in the client's memory.

    `src/api.rs` holds three handlers, wired into an axum `Router` in `src/main.rs`:
    - `POST /register` takes `{nick, password}`, inserts `nick`, `lowercase(nick)` and the password hash, and answers 201 with an empty body.
    - `POST /login` takes `{nick, password}`, looks the user up by lowercased nick, verifies the password, generates a token, stores its hash with `expires_at` = now + 12 hours (D-03), and answers 200 with `{"token": "<base64url>", "expires": <unix epoch seconds>}`.
    - `POST /validate` takes `{nick, token}` and answers 200 with `{"nick": "<the exact casing stored at registration>"}`. Consumption is the security-critical part: select the user's unexpired, unconsumed token rows, argon2-verify the presented token against each, and on a match run a single `UPDATE tokens SET consumed_at = ? WHERE id = ? AND consumed_at IS NULL`, then require `changes()` to equal 1 before answering 200. That predicate is the atomic compare-and-swap that makes a token single-use even if two validate calls race; a select-then-update without the `consumed_at IS NULL` predicate is the replay hole this design exists to close.

    `src/main.rs` reads `AUTH_BIND` (default `127.0.0.1:8081`) and `AUTH_DB` (required, no default) from the environment, parses the bind address, and **refuses to start if the address is not a loopback address** — exit non-zero with a message naming the offending address. D-16 says nothing new is exposed to the internet; a config typo must not be able to violate that, so the guard lives in the binary, not in the unit file. Serve with `into_make_service_with_connect_info` so Task 2's per-IP limiter can see the peer address. A `serve` first argument selects the server; any other first argument is an error for now with a usage line naming the subcommands Task 2 adds.

    Write `scripts/auth-smoke.sh` in the house style (`set -euo pipefail`, `SCRIPT_DIR`/`ROOT_DIR`). It must be repeatable an unlimited number of times and must never touch the production database: it creates a temp DB path under `mktemp -d`, starts `auth-service/target/release/campfire-auth serve` with `AUTH_BIND=127.0.0.1:8099` and that temp `AUTH_DB`, polls `/status` or a TCP connect until the port answers (up to 10 s), runs its assertions, and kills the child and removes the temp directory through an EXIT trap so an aborted run leaves nothing behind. Each assertion prints a named PASS line; a failed assertion prints the expected and actual value and exits non-zero. Keep a check counter and print `SMOKE OK (<n> checks)` as the final line. This task's assertions are the happy path only: register a fresh nick returns 201; login with the right password returns 200 with a token at least 40 characters long and an `expires` at least 11 hours in the future; validate that nick with that token returns 200.

    Build with `nice -n 10 cargo build --release -j2` so the game server keeps its cores. Add `auth-service/target/` and `auth/` to `.gitignore`.

  <action>
    Make each behavior above true, in that order, in the handlers written in Task 1.

    Validation happens before any database work. The nick pattern is exactly D-04's `^[A-Za-z0-9_]{3,16}$` — implement it as a character-class and length check rather than adding a regex crate. The password minimum is 8 characters counted as characters, not bytes. Malformed JSON must surface as 400: axum's JSON extractor rejection defaults to a 4xx already, so confirm the actual status rather than assuming, and map it explicitly if it is not 400. Error bodies are a single `error` field with a stable machine-readable string (`nick_taken`, `invalid_nick`, `weak_password`, `bad_json`, `invalid_credentials`, `invalid_token`, `rate_limited`) — Phase 4's launcher shows human messages for these, so they are part of the contract Task 3 documents.

    Wrong password and unknown nick must return the same status and the same error string. Do not skip the argon2 verification for an unknown nick either — verify against a fixed dummy hash so the two paths cost the same, which keeps a caller from enumerating registered nicks by response timing.

    Rate limiting goes in `src/ratelimit.rs` as a `Mutex<HashMap<IpAddr, Vec<Instant>>>` in the shared state, pruned on each check. RESEARCH.md's own recommendation is that a single endpoint at this traffic scale does not justify learning `tower-governor`'s builder API, and a hand-rolled sliding window of ~15 lines is the lazier correct answer here. Two policies: `/register` allows 5 attempts per hour per peer address (D-04, counting every attempt); `/login` allows 10 **failed** attempts per hour per peer address, counting only failures so that testing and normal launcher use are never throttled. `/validate` is never rate limited — it is the join path and the caller is the game server on loopback. The peer address comes from `ConnectInfo`; add a comment recording that when Phase 3 puts Caddy in front of this service every request will arrive from 127.0.0.1, so Phase 3 must either keep these endpoints direct or teach this limiter to read a forwarded-for header from a trusted proxy. Task 3 repeats that warning in the README.

    `GET /status` returns the fixed placeholder `{"online": true, "players": null}`. RESEARCH.md's open question 2 resolves this way for this phase: no RCON call, no player count, until Phase 3 or Phase 4 actually needs the number.

It asks for no password on purpose: it can only run for someone who can already open the mode-600 database, which is strictly more privilege than knowing the password, so a password prompt here would be theatre. Record that reasoning as a comment above the subcommand so a later reviewer does not read it as an authentication bypass. `campfire-auth reset <nick>` reads a new password from stdin, applies the same length rule as registration, and replaces the stored hash. Both subcommands exit non-zero with a clear message for an unknown nick.
