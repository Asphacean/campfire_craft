      You need the RLCraft client you hand-installed in Phase 1 (`docs/CLIENT-SETUP.md`).

      Preparation:
      1. **Mod onto your client.** From your PC: `scp <pi-user>@<pi-address>:~/rlcraft/mods-src/campfire-auth/build/libs/campfire-auth-0.1.0.jar .` and move it into your client's `mods/` folder, alongside the rest of the RLCraft mods.       2. **Create your account.** On the Pi: `curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'content-type: application/json' -d '{"nick":"<YourNick>","password":"<at least 8 chars>"}' http://127.0.0.1:8081/register` — it must print `201`. Use the **exact** capitalisation you play under: the game turns your nick into your player ID by hashing the exact letters, so `Steve` and `steve` are two different players with two different inventories.       3. **Mint a token.** On the Pi: `campfire-auth login <YourNick>`. It prints one line — that is your token, good for exactly **one** join. Mint a fresh one for every join. This is what the Phase-4 launcher will do for you; right now you are the launcher.

      **Test A — with a token (must let you in).** Add two JVM arguments to your launcher profile: `-Dcampfire.nick=<YourNick>` and `-Dcampfire.token=<the token>`. Connect to `mc.campfire.pub`. Expected: you join normally. Then report three things: can you **move**, can you **break a block**, can you **send a chat message**? For a second or two on join you may float and be unable to act — that is the freeze while the server checks your token. Still stuck after five seconds is a defect.

      **Test B — without a token (must turn you away).** Remove both `-D` arguments and connect again. Expected: kicked before you can do anything, with the message `Зайди через лаунчер campfire.pub / Join via the campfire.pub launcher`. Report the **exact** text you saw — a generic Forge or Minecraft error instead is a different failure and needs to be known.

      **Test C — optional.** If you have a plain vanilla (non-RLCraft) client, point it at the server under your nick and report what it says. Either message is acceptable; the point is to record which one.

      Report back: the nick you registered; whether Test A let you in and whether you could move, break a block and chat; the verbatim Test B text; and the Test C result if you ran it. Never paste the token itself.

      Cross-check on the Pi once you report: `server/logs/latest.log` must show a `[campfireauth]` line with `result=allow` for Test A and `result=kick` with a reason for Test B, and reusing the Test A token must fail.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Built jar → live game server | Code from a build directory starts running against everyone's world |
| Enforcement state → the friend group | A wrong turn here locks out the people the server exists for, including the operator |
| Nick namespace → existing player data | Phase 1 ran open, so nicks with real progress exist that have no account behind them yet |
| Operator's PC → server | The only place a real client token exchange is exercised |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03-01 | Denial of Service | the enforcement restart itself | high | mitigate | RCON `list` before, an announcement and a sixty-second wait if anyone is online, exactly one `systemctl restart`, and a pre-restart backup containing both world and accounts |
| T-02-03-02 | Denial of Service | the gate misbehaving and locking everyone out | high | mitigate | A one-jar-deletion-plus-one-restart rollback written into `docs/AUTH-OPS.md` before the restart happens, not after; RCON remains reachable on loopback regardless (D-10) |
| T-02-03-03 | Spoofing | someone registering a nick that already owns another player's progress | high | mitigate | The nick inventory from `usercache.json` and `world/playerdata/` is produced before enforcement and handed to the operator at the checkpoint so those nicks get claimed; residual risk accepted per D-14, with `campfire-auth reset` as the dispute remedy |
| T-02-03-04 | Denial of Service | the auth service stopped during an incident | high | mitigate | `docs/AUTH-OPS.md` states explicitly that stopping `campfire-auth.service` now locks every player out and is never the right first move; acceptance criteria assert it is `active` at the end of every task |
| T-02-03-05 | Information Disclosure | secrets travelling inside the jar shipped to clients | medium | mitigate | The jar is built from tracked sources with no configuration baked in; verify with `unzip -p <jar> | strings | grep -cF "$RCON_PASSWORD"` returning `0` before it is copied to the operator's PC |
| T-02-03-06 | Information Disclosure | a token pasted into a chat or a screenshot during the client test | low | accept | Tokens are single-use and expire in twelve hours; the human-check instructions ask for outcomes and say explicitly never to paste the token |
| T-02-03-07 | Tampering | a stale jar left alongside the new one in `server/mods` | medium | mitigate | Acceptance criterion counts exactly one `campfire-auth-*.jar` and compares its sha256 against the build output |
</threat_model>
