<objective>
Build the enforcement point: one Forge 1.12.2 mod, built on this Pi, that freezes every joining player, asks their client for the launcher-issued token, checks it against the auth service over loopback, and kicks on anything less than a clean 200. Prove it works on a throwaway server before it ever goes near the one people play on.

**Goal (quoted verbatim from ROADMAP.md Phase 2** — not in user-story form; nothing invented in its place**):** *Only a registered nick presenting a valid token can play; anyone with a vanilla client is turned away.*

Purpose: AUTH-04 and AUTH-05. This mod is the entire enforcement layer — an offline-mode server has no protocol-level identity check at all, so every security property of this project rests on the code in this plan being fail-closed.
Output: `campfire-auth-0.1.0.jar` plus the evidence that it refuses a tokenless join.

Phase 2 decision IDs (D-01 … D-16) are defined in the table in `02-01-PLAN.md`. This plan implements D-06, D-07, D-08, D-09, D-10, D-15 and the mod half of D-16.

    **The mod (D-06, D-08, D-09).** One Gradle project, one jar, shared sources with the side split done by annotation, so the server copy and the client copy can never drift apart.

    `CampfireAuth` is the `@Mod` entry point with modid `campfireauth`, name `Campfire Auth`, version `0.1.0`, and — this one matters — `acceptableRemoteVersions` set to accept any remote version. Without it, Forge's own handshake rejects a client that lacks the mod before our code ever runs, and the player sees a generic Forge mod-mismatch screen instead of the bilingual instruction to use the launcher. With it, our gate does the refusing and controls the message. Register the network channel in preInit.

    `NetworkHandler` creates the channel with `NetworkRegistry.INSTANCE.newSimpleChannel` under the name `campfireauth` — twelve characters, comfortably under the twenty-character cap that Forge 1.12.2 enforces by throwing at mod init (Pitfall 4). Register the request message with discriminator 0 for `Side.CLIENT` and the response message with discriminator 1 for `Side.SERVER`.

    `AuthRequestMessage` is an empty-payload server-to-client packet. Its handler is client-side and does exactly what Pattern 1 prescribes: read the two JVM system properties `campfire.nick` and `campfire.token`, and return an `AuthResponseMessage` built from them. Reading a system property has no dependency on the player entity existing, which is precisely why this design does not touch the client connect event at all — that event fires before the player object exists and is the documented source of intermittent null-pointer failures on slower connections (Pitfall 1). Missing properties become empty strings, not an exception: an unconfigured client must be kicked by the server, not crash on itself.

    `AuthResponseMessage` carries two strings, written and read with Forge's UTF-8 byte-buffer helpers. Reading is the only place in this mod where fully attacker-controlled bytes are parsed, so bound it: reject a nick or token longer than 256 characters by treating the message as invalid rather than allocating whatever length the client claims. Its handler runs on the network thread — do no game-state work there; hand the payload to the main thread through the server instance's scheduled-task queue and return null.

    `ServerAuthHandler` is a dedicated-server-side event subscriber holding one pending-join map keyed by player UUID, with the join timestamp, the player's game type as it was before the freeze, and their position at join.
    - On `PlayerEvent.PlayerLoggedInEvent`: on the main thread, record the entry, put the player into spectator game type, remember where they were standing, and send the request packet. Spectator is the freeze (Pattern 2): one state Mojang already maintains, covering movement into the world, block breaking, interaction and attacking at once, instead of four separate event cancellations each with their own edge cases. Log the join at INFO with the nick and no token.
    - On `ServerChatEvent` and `CommandEvent`: cancel the event if that player's UUID is still pending. Spectator mode does not block chat, and CONTEXT.md's freeze list includes chat, so this is the one addition Pattern 2 explicitly calls for — and it is exactly one addition, not the start of a pile of hand-rolled cancellations.
    - On `TickEvent.ServerTickEvent`: sweep the pending map and kick anyone who has been pending for more than five seconds (D-09). This is the case a vanilla or launcher-less client falls into — it never replies, so the timeout is what turns it away.
    - On the response arriving: compare the packet's nick against the connected player's own profile name and kick on a mismatch. The packet's nick field is client-supplied and must never be treated as identity — the nick sent to `/validate` is the one the server already knows from the connection, and the packet contributes only the token. Then spawn a plain thread named for this mod that POSTs `{nick, token}` as JSON to `http://127.0.0.1:8081/validate` with a three-second connect timeout and a three-second read timeout, and deliver the boolean result back to the main thread through the scheduled-task queue (Pattern 3). One thread per join is right at this scale; do not build an executor or a connection pool.
    - The result variable starts false and is only ever set true by an explicit 200. Any exception, timeout, connection refusal, non-200 status or unparseable answer leaves it false and the player is kicked. This is the load-bearing property of the entire project: an auth service that is down must lock everyone out, never let everyone in.
    - On a true result: restore the remembered game type, put the player back at the remembered position, remove the pending entry, and log `result=allow`. On false: `player.connection.disconnect` with the bilingual message from D-15, and log `result=kick` with a machine-readable reason of `no_packet`, `nick_mismatch`, `invalid_token` or `service_error`.
    - On `PlayerEvent.PlayerLoggedOutEvent`: drop the pending entry so a disconnect during validation cannot leak an entry or resurrect a stale freeze.
    - Log lines use a single `[campfireauth]` prefix and include the nick and the reason. They never include the token or any part of it — the log is the most-copied artifact on the box and a token in it is a live credential for twelve hours.

    `ClientAuthHandler` holds the client-only property reads behind the client-side annotation so the class is never loaded on the dedicated server.

    `scripts/join-probe.py` is a dependency-free Python 3 client speaking just enough of the 1.12.2 protocol to trigger a login and read what comes back. It reports the first disconnect it receives, whether that arrives in the login state or the play state, printing the raw JSON reason and exiting 0; if nothing arrives within the timeout it prints a distinct no-disconnect marker and exits non-zero. Keep it small and obvious; it is a test instrument, not a client library.

    With a token supplied, the probe additionally watches for the server's custom-payload packet on the `campfireauth` channel and answers it with a serverbound custom payload carrying the two length-prefixed UTF-8 strings the mod's response message expects. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Player's client → game server plugin channel | Fully attacker-controlled bytes and an attacker-chosen nick claim arrive here |
| Game server mod → auth service (loopback HTTP) | The mod delegates the only identity decision in the system across this line |
| Gradle build → Maven artifacts | A build-time compromise here ships straight into the jar that runs on the server and on every friend's PC |
| Dev test server → the host's network | A second Minecraft server on the same box is a new listener that must not become a new exposure |
