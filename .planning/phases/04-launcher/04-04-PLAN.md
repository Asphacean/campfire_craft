## Two things resolved during planning that the UI contract left open

`04-UI-SPEC.md` closes with two items marked as needing a decision at plan time. Both were resolved by inspection, and neither needs to reach the executor as an open question:

1. **The nick field's maximum length.** The auth service accepts three to sixteen characters of ASCII alphanumerics and underscores. Sixteen characters at the heading size is far inside a 480-pixel window, so the collapsed logged-in line **cannot** overflow and needs no truncation rule — the input's own maximum length is the whole fix. Wave 1 already set it.
2. **Whether usable RLCraft art can be sourced.** It can. `pack/resources/mainmenu/background.png` (1920×1017) and `pack/resources/mainmenu/rlcraft_logo_1_edit.png` (2000×1000, with transparency) are on this Pi already, extracted from the client pack. They ship as-is, copied verbatim with no resizing step, because the webview scales them and this host has no image tooling — 3.7 MB inside the binary is a fair price for not adding a dependency to crop a picture. Licensing sits under the same accepted-risk decision the operator recorded for the pack itself in Phase 3: these are RLCraft's own assets, already being served to the same closed group of friends, and the launcher is not published beyond them. The dark-minimalism fallback path in the stylesheet stays in place, so the contract holds either way.

## Claude's discretion, exercised here

| Choice | Decision taken | Why |
|--------|----------------|-----|
| Where the updater logic lives | The check runs in Rust and the window renders our own dialog; no updater package is imported into the frontend | Consistent with the whole no-npm decision from wave 1 — the plugin has a perfectly good Rust API, and one more in-window dialog is cheaper than a package manager |
| Physical memory detection | The `sysinfo` crate, one call, at startup | Checked against crates.io during planning: `OK`, 3.4M downloads a week, first published 2015. The alternative is two platform-specific system calls behind `cfg` blocks, which is more code and more unsafe for the same number |
| Log rotation | One generation at a couple of megabytes | It is a diagnostic a friend pastes into chat, not an audit trail |
| Where the update feed lives | `launcher-dist/` on the Pi, served at the launcher route wave 1 already opened, deliberately outside the pack tree | The manifest generator walks everything under the pack root; launcher binaries inside it would be published as managed pack files and downloaded into every player's game directory |
| What "self-update works" means in this phase | The check, the feed, the signature configuration and the publish command are all real and asserted; the download-and-restart round trip is proven on the operator's own machine and, for the shipped platforms, by Phase 5's release build | This host is aarch64 Linux and is not a shipped target. Building a throwaway Linux release artifact purely to watch it replace itself would be work for a platform with no players |
| The two options files and the server list | Already handled in waves 2 and 3; this plan only surfaces the pack version in the footer | Named here so nobody re-implements seeding in the UI layer |
