<objective>
Turn a directory of mods into a game that can actually start: Minecraft's own files from Minecraft's own servers, Forge installed by Forge's own installer, and a launch command line that is complete enough to run.

**Goal (quoted verbatim from ROADMAP.md Phase 4** — not in user-story form; see `04-01-PLAN.md` for why nothing has been invented in its place**):** *A friend goes from opening the launcher to playing on the server with no manual setup of Java, Forge, or mods.*

This plan's slice of that story: *everything the game needs to start exists on disk, and the exact command that starts it has been built and printed.*

Purpose: LNCH-04. The riskiest unknown in this phase — whether Forge's 1.12.2 installer can be driven without a display — was settled empirically during research on this very Pi, including the undocumented profile-stub prerequisite it silently needs. This plan turns that finding into code and re-runs it as the launcher.
Output: `mojang.rs`, `forge.rs` and `launch.rs` in the core, plus a real, complete game directory on this Pi built by `campfire-cli bootstrap` and a real launch line printed by `campfire-cli launch-cmd`.

## The one thing research settled that changes the plan

`04-CONTEXT.md`'s D-15 says to auto-connect with `--server`/`--port` "if it works with Forge 1.12.2, else rely on the seeded servers.dat". Research checked and there is **no such placeholder** in either the vanilla 1.12.2 argument template fetched live from Mojang or the Forge version's own template. So CONTEXT's own fallback is promoted to the primary mechanism: **the seeded server list is how a player reaches campfire.pub.** The two flags are still appended to the game arguments, because LaunchWrapper passes unrecognised arguments through and vanilla's own option parser has historically accepted them — if they work, the player gets true autoconnect for free; if they are ignored, the seeded list already covers it. They are the only optional part of the whole command line, and the operator check in wave 4 says exactly what to do if the game refuses to start with them present.

## Claude's discretion, exercised here

| Choice | Decision taken | Why |
|--------|----------------|-----|
| The server list file | A precomputed one-entry NBT blob committed as `core/assets/servers.dat` and embedded with `include_bytes!`, rather than an NBT writer | The file's contents never vary — one server, one name, one address, all fixed for the life of this project. A static blob is fifteen bytes of code; an NBT serialiser is a crate or a hundred lines, for a file with exactly one possible value |
| Where the Forge installer comes from | Downloaded from Forge's own maven at `https://maven.minecraftforge.net/net/minecraftforge/forge/1.12.2-14.23.5.2860/forge-1.12.2-14.23.5.2860-installer.jar` through the public client, and pinned to sha256 `ea7c33ba95e3993a98d0e9e38168c0759ec323a18675a71d938e1f3f70e6e8e7` — the hash of the copy already sitting in this repository's `downloads/`, so the pin is measured rather than copied from a webpage | The maven path is a direct artifact URL, not the ad-supported download page the installer's own embedded note asks tooling to respect. Pinning the hash means a compromised maven cannot swap the jar that is about to be executed with the player's own privileges |
| JVM flags | The Aikar-family G1 set from research, plus `-Dfml.ignoreInvalidMinecraftCertificates=true` and `-Dfml.ignorePatchDiscrepancies=true`, all in one named constant | CONTEXT leaves the flag set to discretion. Research also names the correct response if the game will not start: drop to bare heap flags rather than debugging GC tuning. Keeping them in one constant makes that a one-line change |
| Asset download concurrency | Eight at a time for the asset objects, four for everything else | The asset index is roughly 3,700 tiny files against Mojang's CDN, which is a different shape of work from a hundred multi-megabyte jars off a Pi |
| Merge strategy | The Forge JSON's `inheritsFrom` parent is loaded and merged with the child winning on `mainClass` and `minecraftArguments`, and the child's libraries placed **before** the parent's on the classpath | This is the ordering every launcher uses for this Forge generation, and the reason a patched library shadows the vanilla one |
| Spawning | The core builds and returns the argument vector; spawning is a separate call that takes it | It is what makes the command line assertable on a machine that cannot run the game, which is every machine available to this executor |

## What this plan does not touch

No service on this Pi is restarted, reconfigured or stopped, and the Pi is never rebooted. The Forge installer runs as an ordinary user process against a scratch directory under `/tmp`, using the Java 8 already installed for the game server, and never writes into `server/`, `pack/` or the live game's directory.

**Facts verified live during research — treat as settled, do not re-derive:**

- The Forge installer fails on a fresh directory with `There is no minecraft launcher profile in "<dir>", you need to run the launcher first!` and `There was an error during installation`, exits without crashing, and needs **no display**. Pre-seeding this exact stub in the target directory makes the same command succeed completely headlessly:
  `{"profiles":{},"selectedProfile":"","clientToken":"00000000-0000-0000-0000-000000000000","authenticationDatabase":{}}`
- The command is `java -jar forge-1.12.2-14.23.5.2860-installer.jar --installClient <game-dir>`. Passing the recognised CLI flag is what avoids the GUI-wizard path that crashes on a headless Linux box.
- The produced file is `versions/1.12.2-forge-14.23.5.2860/1.12.2-forge-14.23.5.2860.json` — note the `-forge-` separator — and it is an ordinary Mojang-shaped version JSON:
  `"id": "1.12.2-forge-14.23.5.2860"`, `"inheritsFrom": "1.12.2"`, `"mainClass": "net.minecraft.launchwrapper.Launch"`, 21 libraries, and
  `"minecraftArguments": "--username ${auth_player_name} --version ${version_name} --gameDir ${game_directory} --assetsDir ${assets_root} --assetIndex ${assets_index_name} --uuid ${auth_uuid} --accessToken ${auth_access_token} --userType ${user_type} --tweakClass net.minecraftforge.fml.common.launcher.FMLTweaker --versionType Forge"`
- **No processor or binpatch metadata survives into that JSON.** Nothing Forge-specific has to be interpreted at launch time.
- One library entry has an **empty** download URL and is written directly by the installer from its own embedded copy:
  `{"name":"net.minecraftforge:forge:1.12.2-14.23.5.2860","downloads":{"artifact":{"path":"net/minecraftforge/forge/1.12.2-14.23.5.2860/forge-1.12.2-14.23.5.2860.jar","url":"","sha1":"029250575d3aa2cf80b56dffb66238a1eeaea2ac","size":4466148}}}`
  The download builder must special-case `url == ""`: never fetch it, only assert it exists at `path` with that SHA-1.
- The vanilla 1.12.2 argument template is `--username ${auth_player_name} --version ${version_name} --gameDir ${game_directory} --assetsDir ${assets_root} --assetIndex ${assets_index_name} --uuid ${auth_uuid} --accessToken ${auth_access_token} --userType ${user_type} --versionType ${version_type}` — there is **no** `--server` or `--port` placeholder anywhere.
- Mojang's chain: `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json` → the 1.12.2 entry's `url` → that version JSON, whose `downloads.client` gives the client jar with a SHA-1, whose `libraries[]` carry `rules`, `natives` and `downloads.classifiers`, and whose `assetIndex` (id `1.12`) points at an index whose objects live at `https://resources.download.minecraft.net/<first two hex chars>/<full hash>`. Mojang hashes are **SHA-1**, not the SHA-256 the pack manifest uses — do not conflate the two hash domains.

**The token handoff contract**, verified by reading `mods-src/campfire-auth/src/main/java/pub/campfire/auth/client/ClientAuthHandler.java`: the client mod reads exactly `System.getProperty("campfire.nick", "")` and `System.getProperty("campfire.token", "")` and nothing else. Two `-D` properties are the complete contract; no extra file, no extra flag.

**The JVM flag set** (research, Aikar-family, client-scaled):
`-XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200 -XX:+UnlockExperimentalVMOptions -XX:+DisableExplicitGC -XX:+AlwaysPreTouch -XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 -XX:G1HeapRegionSize=8M -XX:G1ReservePercent=20 -XX:G1HeapWastePercent=5 -XX:G1MixedGCCountTarget=4 -XX:InitiatingHeapOccupancyPercent=15 -XX:G1MixedGCLiveThresholdPercent=90 -XX:G1RSetUpdatingPauseTimePercent=5 -XX:SurvivorRatio=32 -XX:+PerfDisableSharedMem -XX:MaxTenuringThreshold=1`
plus `-Dfml.ignoreInvalidMinecraftCertificates=true -Dfml.ignorePatchDiscrepancies=true`.

**Nick casing** (`docs/DIST-OPS.md`): always pass through the exact casing the auth service returned, never a player-retyped variant and never the lowercased uniqueness key. The offline UUID is derived from the exact username byte string, so a case drift silently orphans a player's inventory with no error at all.
