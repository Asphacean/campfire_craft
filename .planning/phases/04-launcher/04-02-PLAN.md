<objective>
Get the game's files onto a machine: the modpack from our own host, and a Java 8 that our own launcher owns. Both halves are proven here, headlessly, against the live production endpoints — not against fixtures.

**Goal (quoted verbatim from ROADMAP.md Phase 4** — not in user-story form; see `04-01-PLAN.md` for why nothing has been invented in its place**):** *A friend goes from opening the launcher to playing on the server with no manual setup of Java, Forge, or mods.*

This plan's slice of that story: *the files arrive, only the changed ones, and my saves are still there afterwards.*

Purpose: LNCH-02 and LNCH-03 in full, plus the reporting half of LNCH-05. `scripts/assemble-client.py` already proved on this Pi that a client can be rebuilt from the manifest alone over a pinned CA — this plan ports that proof into the launcher and then re-runs it as the launcher.
Output: `manifest.rs` and `java.rs` in the core, exercised by `campfire-cli sync`, `campfire-cli verify` and `campfire-cli java-fetch` against `https://mc.campfire.pub:8444` and `https://api.adoptium.net`.

## Decision IDs implemented here

The full Phase 4 decision table is in `04-01-PLAN.md`'s objective. This plan implements **D-10, D-14 and D-19**, and provides the reporting mechanism **D-07** consumes in wave 4. It also honours **D-12** by refusing to let our own host serve anything Mojang owns, and **D-13** by resolving every path through `paths.rs`.

## Claude's discretion, exercised here

| Choice | Decision taken | Why |
|--------|----------------|-----|
| Download concurrency | Four at a time, as a fixed constant, via a semaphore over the shared `reqwest` client | D-19 names four. A single Caddy on a Pi serving one friend does not want more, and a constant needs no configuration surface |
| Progress granularity | One event per completed file plus a periodic byte-rate tick, not one event per chunk | The pack is roughly 190 files; per-file is already fine-grained enough for a progress bar, and per-chunk would flood the channel wave 4 attaches |
| Where the seeded client options come from | The two files are extracted once from the cached client zip at `downloads/RLCraft 1.12.2 - Release v2.9.3.zip` and committed as `core/assets/options.txt` and `core/assets/optionsof.txt`, embedded with `include_bytes!` | `docs/DIST-OPS.md` records this as gap 1 that Phase 4 must close: `publish-pack.sh` deliberately drops both files so a publish can never clobber a player's tuned settings, which also means the manifest cannot deliver the pack's own defaults to a fresh install. A committed copy is the smallest thing that closes it, and it is 6 KB |
| Java archive handling | `zip` for the Windows archive and `flate2` + `tar` for the macOS one, extracting into a version-named directory under `runtime/` and then recording the resolved `java` path in a small marker file | Two archive shapes, two crates already in the research audit; the marker file is what makes "is Java already provisioned" a file existence check rather than a re-probe |
| Translated-process detection | A `libc::sysctlbyname` call for `sysctl.proc_translated`, compiled only on macOS, returning a three-state answer (native, translated, unknown) | The research names this exact technique. Three states matter: "unknown" must not be reported to the user as "Rosetta is missing" |
| Unsupported platforms | Linux is an explicit, named error rather than a silent fallthrough, and `campfire-cli java-fetch` takes a `--target` override so this aarch64 Linux host can still exercise the Windows and macOS download paths for real | There is no Linux player and no Linux release (REQUIREMENTS "Out of Scope"), but there is a Linux machine doing all the verification |

## What this plan does not touch

No service on this Pi is restarted, reconfigured or stopped. `rlcraft.service`, `campfire-auth.service` and `caddy.service` are all left exactly as wave 1 left them, and the Pi is never rebooted. The only writes outside the repository are into a scratch install root under `/tmp`.

The manifest contract (`docs/DIST-OPS.md`, Phase 3, locked):

```json
{ "pack_version": "2026-08-28T14:03:11Z", "mc": "1.12.2", "forge": "14.23.5.2860", "java": 8,
  "files": [ { "path": "mods/X.jar", "sha256": "<64 lowercase hex>", "size": 49537, "url": "mods/X.jar" } ],
  "delete": [ "mods/Removed.jar" ] }
```

- `path` is relative to the client instance root; `url` is relative to `/pack/` and is currently identical to `path`, but must be treated as a separate field.
- `delete` is **cumulative** — an entry stays until the file reappears in `files`, so an install several publishes behind still learns about an old removal. Never assume it holds only the last publish's removals.
- Managed: `mods/`, `config/`, `scripts/`, `resources/`, `structures/`, `resourcepacks/` and whatever else the pack's overrides carry.
- **Never managed, never in `files`, never in `delete`, and the launcher must never touch them:** `saves/`, `screenshots/`, `logs/`, `crash-reports/`, `options.txt`, `optionsof.txt`, `servers.dat`.
- Pack file URLs are percent-encoded per path segment — several real filenames contain spaces (`resources/mainmenu/images/4 new.jpg`).

The reference guard, from `scripts/assemble-client.py` (port faithfully, do not redesign):

```python
FORBIDDEN_PREFIXES = ("libraries/", "assets/", "versions/")
for field in ("path", "url"):
    if os.path.isabs(value): reject()
    if ".." in value.split("/"): reject()
    if any(ord(c) < 0x20 or ord(c) == 0x7F for c in value): reject()
    if os.path.commonpath([real_dest, os.path.realpath(os.path.join(dest, value))]) != real_dest: reject()
# plus: reject if path startswith FORBIDDEN_PREFIXES, or basename lowercased starts "minecraft" and ends ".jar"
# plus: every entry must carry all four of path, url, sha256, size
# plus: every delete[] entry gets the absolute/parent-component check too
```

    **`progress.rs` first**, because everything reports through it. A `Progress` enum with a `Step { name, current, total }` variant, a `Bytes { downloaded, total, per_sec }` variant, a `Done` variant and a `Failed { code }` variant, all `Clone + serde::Serialize`. A `ProgressSink` type alias for `&(dyn Fn(Progress) + Send + Sync)` and a no-op sink for tests. The core never knows about Tauri; wave 4's command layer adapts this to a channel.

    **Fetch and pin.** One `GET /manifest.json` through `campfire_client()`, parsed into a typed struct with all five top-level fields plus `files` and `delete`. That parsed value is the authority for the entire run — never re-fetch mid-sync, because a publish landing halfway through would leave a client holding half of each of two packs.

    **Validate before touching disk.** Port the guard exactly: every entry must carry all four fields; `path` and `url` are each rejected if absolute, if any slash-separated component is a parent reference, if any character is a control character, or if joining and canonicalising against the game directory escapes it; `path` is rejected if it starts with the library, asset or version prefixes or if its basename looks like the vanilla client jar; and every `delete` entry gets the absolute and parent-component checks too. A single failure rejects **the whole manifest** and the sync does not begin — a per-entry skip would let an attacker hide one bad entry among 190 good ones. Canonicalisation must not require the file to exist yet, so resolve the game directory itself and then check the joined path lexically after normalising, rather than calling a canonicalise that fails on a missing file.

    **Diff.** For each entry, if the file exists with the manifest's exact size and its sha256 matches, it is up to date and no request is made. Hash with `sha2` streaming in one-megabyte chunks. Report a `Step` event as the hashing pass walks the list, because on a cold-ish disk that pass alone is visible.

    **Download.** At most four concurrent, over the one shared client. Each file goes to a temporary file **in its own destination directory** so the rename is same-filesystem, streams through the hasher as it writes, and is renamed into place only after both size and hash match. Percent-encode each URL path segment while leaving separators alone — several real pack filenames contain spaces and a naive join fails outright on them. On any mismatch, delete the temporary file and record the failure. Emit a `Bytes` event on a timer, not per chunk.

    **Delete.** After all downloads succeed, remove any locally-present file named in `delete`, and prune directories left empty by the removal. Never remove anything not named there.

    **The never-touch rule is a rule in code, not a comment.** Before any write or unlink, assert the target is not `options.txt`, `optionsof.txt` or `servers.dat`, and is not under `saves/`, `screenshots/`, `logs/` or `crash-reports/`. The manifest is contractually incapable of naming them — this is the second lock, for the day the contract slips.

    **Seed once.** On a game directory that has no `options.txt`, write the embedded copy; same for `optionsof.txt`. If either file already exists, never touch it again, on any subsequent sync. Do this after the sync completes, and log which files were seeded.

    **Verify.** A `verify()` entry point that re-hashes every managed file against the pinned manifest and repairs whatever is missing or mismatched by downloading it through the same path, returning a count of checked and repaired files. This is D-19's "Verify files" and it is the same code, not a parallel implementation.

    **Failure shape.** Return an error carrying a variant — network, manifest rejected, hash mismatch, disk full, permission — not a formatted sentence. Disk full deserves its own variant because the UI has a specific sentence for it; detect it from the write error's kind rather than by matching on a message string.

    **The hostile-manifest test suite**, in `core/tests/manifest_guard.rs`. Build manifests in memory and assert each is rejected: an absolute path; a parent-directory component in `path`; the same in `url`; a control character; a path under the library prefix; a basename that looks like the vanilla client jar; a missing `sha256`; a `delete` entry with a parent-directory component.     Give the launcher its own Java 8, per platform, from the vendor's own API, checked against the vendor's own checksum — and make it structurally impossible for the system Java to be used instead.

    **The platform table, as data.** A small table mapping a target to the Adoptium query parameters and the archive shape: Windows x64 to `os=windows&architecture=x64` and a zip; macOS Intel to `os=mac&architecture=x64` and a gzipped tar; macOS Apple Silicon to **the same** `os=mac&architecture=x64` and a gzipped tar, because D-10's locked v1 choice is the x86_64 build under translation rather than an arm64 JRE that does not exist for Java 8 at Adoptium. A table, not a format string — the research explicitly flags the single-template approach as the anti-pattern here. Every other target, Linux included, is a named `UnsupportedPlatform` error carrying the detected target, not a fallthrough.

    **Detect, then override.** Resolve the current target from `std::env::consts::OS` and `ARCH`. Expose that resolution as a public function so the CLI can print it, and let the CLI pass an explicit target instead — that override is the only reason the Windows and macOS paths can be exercised on this aarch64 Linux host at all, and it must never be reachable from the UI.

    **Fetch.** Query the feature-releases endpoint through `public_client()` — Adoptium is a public-CA host and the pinned client physically cannot reach it, which is a feature, not an obstacle. Take the first General Availability entry, read `binaries[0].package.link`, `.checksum` and `.size`, and log the release name. Prefer `package` over `installer` always: the launcher wants a directory it can extract quietly, not an installer with a UI. Stream the download to a temporary file next to the runtime directory, hashing as it goes (Adoptium publishes sha256), emitting `Bytes` progress events. **If the checksum does not match, delete the temporary file and return a `ChecksumMismatch` error — never extract an unverified archive.**

    **Extract.** Zip for Windows, gzipped tar for macOS, into `runtime/<release-name>/` under the install root, into a temporary sibling directory that is renamed into place only after extraction succeeds — a half-extracted runtime that looks present is worse than an absent one. Apply the same path guard the manifest module uses to every archive entry name before writing it: an archive is third-party bytes and a crafted entry name is the classic way out of the extraction directory. Then resolve the java executable — `bin/java.exe` under the extracted root on Windows, `Contents/Home/bin/java` on macOS — assert it exists, and write its path into a `runtime/current.json` marker alongside the release name and the target.

    **Idempotence.** `ensure_java(target)` returns the recorded path immediately if the marker exists and the executable it names is still there; otherwise it does the whole fetch. Nothing re-downloads a JRE that is already provisioned.
