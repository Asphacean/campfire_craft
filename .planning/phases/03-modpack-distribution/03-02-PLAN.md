<objective>
Fill the pipe that plan 03-01 built. Take the official RLCraft 2.9.3 **client** pack, put our configs and our auth mod on top of it, and turn the whole tree into a hashed manifest the operator regenerates with one command — then prove the manifest is complete and correct by building a client from nothing but it.

**Goal (quoted verbatim from ROADMAP.md Phase 3** — this Goal line is not in `As a` / `I want to` / `so that` user-story form, and nothing has been invented in its place**):** *The exact pack the server runs is fetchable over HTTPS with per-file hashes, so any client can be brought into sync.*

Purpose: DIST-01's content half, all of DIST-02, and DIST-03 as the operator redefined it. This is the artifact Phase 4's launcher is built entirely around.
Output: `scripts/publish-pack.sh` as the one operator command, a real several-hundred-megabyte pack behind the HTTPS front, a manifest with a hash for every managed file, and `scripts/assemble-client.py` standing as the repeatable proof that a client can be reconstructed from it.

## Phase 3 Decision IDs

The full table is in `03-01-PLAN.md`'s objective. This plan implements **D-06, D-07, D-08, D-09, D-10 and D-13**, and honours D-12 (the pack tree is deliberately absent from the backups) and D-14.

## Claude's discretion, exercised here

| Choice | Decision taken |
|--------|----------------|
| Manifest generator language | Python 3, standard library only — `hashlib` for streaming sha256, `tempfile` plus `os.replace` for the atomic write. Bash drives acquisition, Python does hashing and JSON, matching how the project already splits `fetch-pack.sh` from `join-probe.py` |
| Hashing parallelism | None. A single sorted pass is a few seconds on this hardware for a pack of this size, and a thread pool would buy nothing but nondeterministic ordering risk |
| `pack_version` | ISO-8601 UTC timestamp — human-legible in a launcher's log, monotone, and diffable, which a counter is not |
| `delete[]` semantics | The locked decision is "diff against the previous manifest". Implemented as the union of the previous manifest's own `delete` entries that are still absent, plus paths present in the previous `files` and absent from the current one. A client three publishes behind still learns about a file removed two publishes ago; a plain one-step diff would strand it |
| Re-publish ergonomics | `--skip-fetch` re-hashes and re-publishes from the pack already on disk without touching CurseForge, so the common case — the operator edited a config — is fast. The default, with no flag, is the full acquisition run |
</objective>

    Write `scripts/gen-manifest.py` and make it the last step of `scripts/publish-pack.sh`, so that DIST-02's "one command" is literally one command. Python 3, standard library only — no third-party import may appear in this file.

    The generator takes the pack root and writes `manifest.json` inside it. It walks the managed content, hashes it, checks it, diffs it and swaps it in atomically.

    Walk: recurse the pack root and collect every regular file except `manifest.json` itself, any dotfile or dotdirectory, and anything under the never-managed set from D-08 — `saves/`, `screenshots/`, `logs/`, `crash-reports/`, and the files `options.txt`, `optionsof.txt`, `servers.dat`. **Sort the collected relative paths explicitly** before doing anything else with them; the walk order is not guaranteed and an unsorted list makes two identical publishes produce differently-ordered manifests, which both makes review noise and makes the delete diff harder to trust.

    Validate every path before it can reach the output. A relative path must not be absolute, must not contain a `..` component, must not contain a null or control character, and its real path must resolve inside the real path of the pack root. Any path failing this is a hard error that aborts the whole run with a message naming the path — this is the write side of the traversal control, and the manifest is the document a launcher will trust, so a bad entry must never be published at all rather than published and hoped-about.

    Apply the forbidden-content gate. Abort the run, non-zero, naming every offender, if any collected path's basename matches `server.properties`, `ops.json`, `whitelist.json`, `usercache.json`, `server.env`, `eula.txt`, a `banned-` prefix, or a `.db` suffix, or if any path component is `saves`. These are files that exist elsewhere in this repository and would be catastrophic to publish to the internet; a static file server has no second chance, so the gate lives here, before the manifest that advertises them is ever written.

    Hash: for each path, a streaming sha256 read in one-megabyte chunks, and the size from the file's own stat. Build each entry as the four fields D-08 specifies — `path` relative to the client instance root, `sha256` as lowercase hex, `size` in bytes, and `url` as the same relative path, since the file server is rooted at the pack directory and the route table maps the pack prefix onto it one-to-one.

    Diff: read the existing `manifest.json` if there is one, before overwriting it. The new `delete` array is the union of two sets — the previous manifest's own `delete` entries whose paths are still absent from the current file list, and the paths that were in the previous `files` and are not in the current one — sorted. Carrying the old entries forward is what lets a client three publishes behind still learn about a file removed two publishes ago; a plain one-step diff would strand it with a stale jar that breaks its mod list. A missing or unreadable previous manifest is not an error: start with an empty delete list and say so.

    Write: assemble the object with `pack_version` as the current UTC time in ISO-8601 with a trailing Z, `mc` "1.12.2", `forge` "14.23.5.2860", `java` 8, then `files` and `delete`. Serialise with sorted keys and an indent so the file is reviewable. Write it through a temporary file created in the destination directory and swapped in with `os.replace`, which is atomic on a same-filesystem POSIX rename; remove the temporary file if anything raises. A reader must never be able to observe a manifest half-written or referencing files that are not all in place. Finish by printing a one-line summary — the file count, the delete count, the total byte size and the `pack_version` — and by chmod'ing the manifest to 644 so the web server can read it.

    Wire it into `scripts/publish-pack.sh` as the final step, invoked with the pack root, and make the publish command's exit status reflect the generator's. Then extend the publish script's closing summary with the manifest's own summary line, and print the exact `curl` command an operator can paste to confirm the new manifest is live.

### manifest.json schema (D-08, as generated by this plan)

`{ "pack_version": "<ISO-8601 UTC timestamp, e.g. 2026-08-28T14:03:11Z>", "mc": "1.12.2", "forge": "14.23.5.2860", "java": 8, "files": [ { "path": "mods/SpawnerControl-1.6.3b.jar", "sha256": "<64 lowercase hex>", "size": 49537, "url": "mods/SpawnerControl-1.6.3b.jar" } ], "delete": [ "mods/SomethingRemoved.jar" ] }`

- `path` is relative to the client instance root; `url` is relative to the `/pack/` route and is currently identical to `path`.
- Managed directories: `mods/`, `config/`, `scripts/`, `resources/`, `structures/`, `resourcepacks/` and anything else the client zip's overrides carry.
- Never managed, never in `files` and never in `delete`: `saves/`, `screenshots/`, `logs/`, `crash-reports/`, `options.txt`, `optionsof.txt`, `servers.dat`.
- `delete` is cumulative: an entry stays until the file reappears, so a client several publishes behind still learns about it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CurseForge CDN → the publish script | Third-party bytes and, more dangerously, third-party **filenames** enter the host here |
| The repository's own tree → `pack/` | Everything that crosses into the pack tree becomes world-readable over the internet; the repository also contains secrets and server-only files |
| `pack/manifest.json` → any client | A document clients trust to decide what to download, delete and execute as mods |
| The HTTPS front → `assemble-client.py` | The client half of the contract: what a downloader must verify before writing a byte to disk |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-02-01 | Tampering | path traversal via a CurseForge-supplied filename | high | mitigate | The fetch loop refuses any resolved filename containing a separator, a `..`, a leading dot or a control character; the manifest generator independently re-validates every path and requires its real path to resolve inside the pack root, aborting the whole run otherwise. | T-03-02-02 | Information Disclosure | a secret or server-only file published to the internet through `pack/` | critical | mitigate | An explicit forbidden-content gate in the generator aborts before writing the manifest if any collected path is a server properties file, an ops/whitelist/banned/usercache list, an env file, an eula, or any `.db`. | T-03-02-03 | Tampering | a truncated or corrupt CurseForge download published as authoritative | high | mitigate | The base zip passes a size floor, a `file` type check and `unzip -t` before its hash is pinned; every published file's sha256 is computed from the bytes on disk at publish time, and `assemble-client.py` re-verifies each one after a round trip through the HTTPS front |
| T-03-02-04 | Tampering | a client observing a manifest that references files not yet in place | medium | mitigate | The manifest is written to a temporary file in the same directory and swapped in with an atomic same-filesystem rename; a failed run leaves the previous manifest byte-identical, which is asserted |
