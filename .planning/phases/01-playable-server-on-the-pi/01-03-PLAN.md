<objective>
Make the world survivable. A scheduled, rotated, consistency-safe backup of the world, plus a restore path that has actually been run once against the live server rather than assumed to work.

Purpose: SRV-03 and ROADMAP success criterion 4 both hinge on the restore having been *performed*, not written. RESEARCH.md Pitfall 4 shows exactly how this silently goes wrong on this server: Forge 1.12.2 keeps the Nether and End inside `world/` as `DIM-1` and `DIM1`, so a script written from Bukkit habits looking for sibling `world_nether`/`world_the_end` directories backs up an incomplete world and nobody finds out until someone walks through a portal.
Output: a six-hourly rotated backup, a restore script, and evidence from a real archive-to-running-server round trip.

Decision IDs (D-01 … D-16) are defined in the table in `01-01-PLAN.md`. This plan implements D-10.
</objective>

  <action>
    Write `scripts/backup.sh` plus the two systemd units, install them, and take real archives.

    `scripts/backup.sh` sources `server.env` and honours `BACKUP_DIR` and `BACKUP_KEEP` as overridable environment variables (so the rotation check below can run with a small retention without editing the file). Sequence, exactly as RESEARCH.md Pattern 2 prescribes:
    1. Create `BACKUP_DIR` with mode 700 if absent, owned by the operator's account (Information Disclosure mitigation — world data carries player nicknames and positions).
    2. Install a shell trap on EXIT that always issues RCON `save-on`, so an abort between save-off and the end of the run cannot leave world saving disabled — the single worst failure mode of this script.
    3. RCON `save-off`, then RCON `save-all`, then sleep 5 seconds so the flush actually lands on disk before anything reads those files.
    4. `tar --zstd -cf "$BACKUP_DIR/world-<UTC timestamp>.tar.zst" -C server world` — one tar of the single `world` tree, with relative paths only. Do not look for sibling nether/end directories: on this server the other dimensions are `world/DIM-1` and `world/DIM1` inside that tree (RESEARCH.md Pitfall 4), and a single `-C server world` covers `level.dat`, `region/`, `playerdata/`, `data/`, `stats/`, `advancements/` and the dimension subdirectories together.
    5. Let the trap run `save-on`, and append a sentinel line to `$BACKUP_DIR/backup.log` recording the archive name, its byte size, the elapsed seconds, and the literal token `save-on ok` once the save-on call has returned successfully. Gate on our own sentinel rather than on the server's localised reply text, which is version-dependent.
    6. Rotate: keep the `BACKUP_KEEP` newest `world-*.tar.zst` files and delete the rest. Never delete `pre-restore-*` archives (plan 01-03 Task 2 writes those and they are the last line of defence during a restore).
    7. Exit non-zero with a named reason if the tar fails, if RCON is unreachable, or if the resulting archive is smaller than 1 MB.

    `systemd/rlcraft-backup.service` is a `Type=oneshot` unit running the script as `User=asphacean` with `EnvironmentFile=/home/asphacean/rlcraft/server.env`. `systemd/rlcraft-backup.timer` uses `OnCalendar=*-*-* 00/6:00:00` (every six hours, D-10), `Persistent=true` so a missed window after downtime still runs, and `WantedBy=timers.target`. Install both with `scripts/install-units.sh` and SUDO `systemctl enable --now rlcraft-backup.timer`.

    Then exercise it for real: run the script once normally; verify the archive's contents; run the rotation twice with retention forced to 1 to prove pruning actually prunes; then take one final normal run so the server ends this task with a current backup in hand.
  </action>

  <action>
    Write `scripts/restore.sh`, then use it to prove a real round trip.

    `scripts/restore.sh` takes an archive path, defaulting to the newest `world-*.tar.zst` in `BACKUP_DIR`, and supports `--help` describing usage and the safety behaviour (this doubles as the operator's restore runbook — no separate document). Sequence:
    1. Validate the archive with `tar --zstd -tf` before touching anything; abort if it does not list `world/level.dat`.
    2. Archive the *current* world first to `$BACKUP_DIR/pre-restore-<UTC timestamp>.tar.zst` — a restore must never be the operation that destroys the only copy of the present state.
    3. SUDO `systemctl stop rlcraft` and confirm the unit reached inactive; abort if it did not (never extract over a world a running JVM holds open).
    4. Move `server/world` aside to a timestamped sibling, extract the archive into `server/`, then remove the moved-aside copy only after extraction succeeds.
    5. SUDO `systemctl start rlcraft`, poll for the startup-complete line, and print a verdict naming the archive restored and the pre-restore safety archive.

    Then run the round trip using a value that lives in `level.dat`, so the proof is about world state and not about file timestamps:
    1. Through RCON, set the `randomTickSpeed` gamerule to 7, then `save-all`.
    2. Run `scripts/backup.sh` — this archive now carries the value 7.
    3. Through RCON, set `randomTickSpeed` back to 3 and `save-all`; query it and confirm the running server reports 3.
    4. Run `scripts/restore.sh` against the archive from step 2.
    5. Query the gamerule again through RCON: it must report 7, which can only be true if world state travelled through the archive and back into the live server.
    6. Set it back to 3 and `save-all`, leaving the server on its normal setting, then take one final backup.
    Also assert the post-restore log is free of chunk-load failure lines, and record in the SUMMARY which archive was restored, the pre-restore archive name, and the restart duration.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Live world files → archive on disk | Data is copied out from under a running JVM; a torn read produces a silently corrupt backup |
| Archive → live world directory | A restore overwrites the authoritative copy of everyone's progress |
| Archive files at rest | World data contains player nicknames, positions and inventories on a Pi shared with other services |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Denial of Service | `scripts/backup.sh` leaving world saving disabled | high | mitigate | Shell EXIT trap issues RCON `save-on` on every exit path including failure; the `save-on ok` sentinel in `backup.log` is an acceptance gate |
| T-03-02 | Tampering | archives taken from a live world | high | mitigate | RCON `save-off` then `save-all` then a 5-second settle before tar, per RESEARCH.md Pattern 2; a plain `tar`/`cp` of a live world is an explicit anti-pattern here |
| T-03-03 | Tampering | `scripts/restore.sh` overwriting the current world | high | mitigate | Pre-restore safety archive written first, service stop confirmed before any extraction, world moved aside rather than deleted, and the old copy removed only after a successful extract |
| T-03-04 | Information Disclosure | `~/rlcraft-backups/` archive contents | medium | mitigate | Directory created mode 700 owned by the operator's account; an acceptance gate asserts the mode. Not on a primary internet-facing boundary, but the Pi hosts other services, so it is mitigated rather than accepted |
| T-03-05 | Tampering | restoring a truncated or wrong-schema archive | high | mitigate | `tar --zstd -tf` validation requiring `world/level.dat` before anything is touched; restore refuses non-zero on a bad archive |
| T-03-06 | Repudiation | no record of which archive was restored when | low | accept | `backup.log` plus the SUMMARY record every archive and the restore; sufficient audit for a single-operator private server |
| T-03-07 | Denial of Service | rotation deleting the only good copy | medium | mitigate | Rotation only ever considers `world-*.tar.zst` and is explicitly forbidden from touching `pre-restore-*` archives; the retention floor is proven by the two-run `BACKUP_KEEP=1` check |
</threat_model>
