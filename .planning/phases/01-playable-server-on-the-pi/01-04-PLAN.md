<objective>
Carry the tracer path from the LAN out to the internet, and find out what the Pi actually does with three people on it. This is the half of the phase goal that needs the operator's router and the operator's friends.

Purpose: SRV-04 and SRV-05 are the two requirements no amount of scripting can assert alone — one needs a router with no CLI, the other needs three humans playing for twenty minutes. Everything automatable around them is automated here: DNS following the public IP, an outside-in reachability probe that does not lie to itself through hairpin NAT, a TPS sampler that produces a number instead of an impression, and the written client path friends need.
Output: the server reachable by domain from outside, a measured TPS record, and a client setup document.

Decision IDs (D-01 … D-16) are defined in the table in `01-01-PLAN.md`. This plan implements D-06, D-07, D-08 and D-13.

**If plan 01-01 recorded `CGNAT_VERDICT=detected`:** SRV-04 is not achievable by port forwarding on this connection. Do not fake it. Run Task 1's checkpoint anyway to confirm the verdict with the operator, then record SRV-04 as blocked with the evidence, note that the remedy is a tunnel or an ISP change (a scope decision, not a Phase 1 fix), and continue with Tasks 2 and 3 in their LAN-only form.
</objective>

  <name>Task 1: Router port forward, DNS A record, and the current forwarding rule list</name>
  <files>server.env (DDNS_PROVIDER, DDNS_API_TOKEN, DDNS_ZONE_ID)</files>
  <action>Forward TCP 25565 to the Pi on your router, point the DNS record at your public IP (or hand me an API token so I do it), and tell me what else your router is forwarding.</action>
  <instructions>
    The server runs, survives crashes and is backed up. Three things need your router and your DNS provider, neither of which I can reach from this Pi:

    1. **Port forward.** In your router's admin page, forward **TCP port 25565 only** to this Pi's LAN address. Do not forward 25575 (that is the RCON console — remote command execution on the server), and do not enable a DMZ host for the Pi. If your router shows the Pi's LAN address as dynamic, set a DHCP reservation or static lease for it first, otherwise the forward silently breaks the next time it renews.
    2. **DNS record.** Create an A record for the domain you gave me earlier, pointing at your current public IP. Two options: do it yourself in your provider's dashboard, or — if your domain is on Cloudflare — paste an API token scoped to *Edit zone DNS* for that zone plus the zone ID, and I will create and then maintain the record automatically.
    3. **Existing forwards.** Tell me every other port-forwarding or UPnP rule the router currently lists. I need to know whether UPnP has quietly opened anything else on this connection, because that is the realistic way the RCON port ends up exposed despite everything we configured on the Pi. If your router has a UPnP rule list, the fastest answer is a screenshot or a copy of the list.

    Also confirm: is the WAN IP the same one you gave me earlier, and does your router page still show the same static/dynamic status?
  </instructions>
  <verification>
    I will write `DDNS_PROVIDER`, `DDNS_API_TOKEN` and `DDNS_ZONE_ID` into `server.env` (mode 600, untracked) if you gave me a token; run `dig +short <domain>` and compare it against the public IP; run the outside-the-LAN status query in Task 2 and require it to report the server online; and record your list of other forwards in the SUMMARY, flagging any rule other than TCP 25565 as a finding rather than accepting it silently. If the record does not resolve yet I will retry with backoff for up to five minutes before reporting a failure, since DNS propagation is not instant.
  </verification>
  <resume-signal>Reply "forwarded" plus: whether you created the A record yourself or are supplying a Cloudflare token (with token and zone ID if so), and the list of any other forwarding/UPnP rules.</resume-signal>
</task>

    First, DNS maintenance, driven by what plan 01-01 recorded (D-07):
    - If `WAN_IP_KIND` is dynamic and `DDNS_PROVIDER` is Cloudflare with a token: SUDO `apt install -y cloudflare-ddns`, configure it from `server.env` (token, zone ID, the record name from `DOMAIN`) with the credential file root-owned and mode 600, enable its systemd timer, and run it once. Prefer this over `ddclient` for a Cloudflare zone — it is a purpose-built oneshot with a systemd timer and no Perl config wizard, per RESEARCH.md's recommendation.
    - If `WAN_IP_KIND` is dynamic on a non-Cloudflare provider: SUDO `apt install -y ddclient` and configure it for that provider's API from `server.env`, same permissions, timer enabled, run once.

    Then write `scripts/reachability.sh`, the standing check for SRV-04:
    1. Source `server.env`; abort with a named error if `DOMAIN` is still the placeholder.
    2. Resolve with `dig +short "$DOMAIN"` and compare against `curl -s ifconfig.me`. Retry with backoff for up to five minutes before failing, since a freshly created record has not propagated everywhere yet.
    3. Ask a third party what it can see, because a probe from this Pi cannot distinguish a working forward from hairpin NAT: query `https://api.mcsrvstat.us/2/$DOMAIN` and require jq to report `.online == true`, plus record the reported version and player count. Note in the script header that this API caches results for a few minutes, so a retry immediately after a router change may return a stale answer — the retry loop must tolerate that rather than treat it as a hard failure on the first attempt.
    4. Print one verdict line and exit 0 only when both the resolution and the third-party check pass.
    Run it and record the output. If the operator's forward list from Task 1 named any port other than TCP 25565, record that as a security finding in the SUMMARY with the port and the rule's source (manual or UPnP).
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → router → Pi TCP 25565 | The one deliberately opened path from the public internet into the home network |
| Router UPnP → forwarding table | Any device on the LAN can ask the router to open a port; this is the realistic route to an exposed RCON port |
| Pi → DNS provider API | A credential that can rewrite the zone's records leaves the Pi on a schedule |
| Pi → api.mcsrvstat.us | A third party is trusted for a reachability signal, and learns the domain |
| docs/CLIENT-SETUP.md → friends (public-ish) | A tracked document that could leak the home IP if written carelessly |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege | router forwarding table / UPnP | high | mitigate | The Task 1 checkpoint requires the operator to forward TCP 25565 only, to refuse a DMZ host, and to report every other rule the router lists; any non-25565 rule is recorded as a finding. The nftables RCON drop from plan 01-02 is the second, Pi-side layer that holds even if the router opens 25575 |
| T-04-02 | Information Disclosure | home public IP in tracked files | medium | mitigate | The client document and the reachability script reference the domain only; an acceptance gate greps both for dotted-quad literals and requires none. The IP lives in `server.env` (untracked) and in DNS |
| T-04-03 | Information Disclosure | DNS provider API token | high | mitigate | Token stored only in `server.env` (mode 600, untracked) and in the updater's own root-owned credential file at mode 600; never echoed into logs or the SUMMARY. The checkpoint asks for a token scoped to edit DNS for the single zone, not an account-wide key |
| T-04-04 | Spoofing | `api.mcsrvstat.us` response used as the reachability verdict | low | accept | Used only as an outside-in signal over HTTPS; a false positive is caught immediately by the friend's real join in the same task's human check, and a false negative only costs a retry |
| T-04-05 | Denial of Service | exposing 25565 to the public internet | medium | mitigate | Whitelist enforcement rejects unknown nicks before world entry, `max-players=10` caps concurrency, and the TPS ladder gives a measured response to load. Residual: an unauthenticated connection flood can still consume tick budget — accepted for a private server whose address is shared only with friends, and revisited by Phase 2's auth gate |
| T-04-06 | Tampering | DNS record pointed at the wrong address by a stale updater | medium | mitigate | `scripts/reachability.sh` compares resolution against the live public IP and fails loudly on drift; it is a standing check the operator can re-run any time |
</threat_model>
