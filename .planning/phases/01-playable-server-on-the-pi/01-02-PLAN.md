<objective>
The tracer slice of this project: one real path from the operator's hand-installed Minecraft client, through the network, into a Forge 1.12.2 server that Temurin 8 runs, that systemd owns, that RCON controls, and that comes back by itself when it dies. Everything later in the phase (backups, internet exposure, TPS tuning) expands outward from this proven path.

Keep `-XX:+UnlockExperimentalVMOptions` ahead of the experimental G1 flags. Abort with a named error if `JAVA8_BIN` does not report 1.8.0 or `SERVER_JAR` is missing.

  <action>
    Three pieces, then prove them.

    **Crash and boot survival (SRV-02).** SUDO `systemctl enable rlcraft`. Then force a real crash: SUDO `systemctl kill -s SIGKILL rlcraft` (SIGKILL, so the JVM dies exactly as it would on an OOM or a hardware fault, bypassing the graceful path), and poll for up to 180 seconds for the unit to be `active` again with a fresh startup-complete line in the log and RCON answering. Record the observed recovery time. Do **not** reboot the Pi to test boot survival — that would kill this executor session; `is-enabled` plus the human reboot check below covers it.

    **Daily graceful restart (D-11).** Create `systemd/rlcraft-restart.service` as a `Type=oneshot` unit whose `ExecStart` is `/usr/bin/systemctl restart rlcraft`, and `systemd/rlcraft-restart.timer` with `OnCalendar=*-*-* 05:00:00`, `Persistent=true`, `WantedBy=timers.target`. Implement it as `systemctl restart` rather than a bare RCON `stop`: an RCON stop exits the JVM cleanly with status 0, and `Restart=on-failure` (D-04) deliberately does not restart a clean exit — a raw RCON stop at 05:00 would leave the server down until someone noticed. `systemctl restart` runs the same `ExecStop` RCON stop, so the world still saves gracefully, and then guarantees the server comes back. Install with `scripts/install-units.sh`, then SUDO `systemctl enable --now rlcraft-restart.timer`.

    **RCON reachable only from the Pi (D-08).** Minecraft 1.12.2 has no property that binds the RCON listener to loopback independently of the game port — `server-ip` would bind both, which would make the game unreachable. So enforce the intent at the host firewall. Write `scripts/harden-rcon.sh` (SUDO) which creates `/etc/nftables.d/rlcraft-rcon.nft` defining a dedicated `table inet rlcraft` with one input-hook chain at a priority ahead of filter, **policy accept**, containing exactly two rules: accept when the input interface is loopback, then drop tcp dport 25575. Scoped table plus accept policy is deliberate — it cannot lock the operator out of SSH or affect any other service on this Pi, unlike a default-drop ruleset. Ensure `/etc/nftables.conf` exists and contains an include line for `/etc/nftables.d/*.nft` (create a minimal file with just the include if it is absent), then SUDO `systemctl enable --now nftables`. Record in the SUMMARY the address `ss` reports the RCON listener actually bound to, so the residual is documented rather than assumed.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet / LAN → TCP 25565 | Untrusted Minecraft clients reach the game port; offline-mode means the protocol itself authenticates nobody |
| Any host → TCP 25575 | The RCON port is remote code execution on the server console for whoever holds the password |
| `server.env` → systemd unit environment | Secrets are handed to a system unit and appear in its process environment |
| Pack zip contents → executed server code | ~200 mods from the archive run in-process with the operator's user rights |
